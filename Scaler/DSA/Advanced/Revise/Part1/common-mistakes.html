Common Mistakes
Part 1 · Days 8–19
Generic pitfalls by technique — not edge cases per problem.
Arrays & Prefix Sum
Not initializing prefix sum at index 0
Prefix sum arrays typically need a leading 0 so that a range starting at index 0 can be computed with a single subtraction. If you start filling from index 0 without a sentinel, range queries for the first element require a special case.
Off-by-one in range queries
Sum of range [L, R] = prefix[R] − prefix[L−1]. A common slip is writing prefix[R] − prefix[L], which excludes the element at L. Always double-check the boundary by tracing a small example.
In-place matrix rotation — swapping the full matrix
When transposing in-place, iterate only over the upper triangle (row < col). If you iterate the whole matrix you swap every pair twice, ending up with the original — a silent no-op that is hard to spot.
In-place sign marking — not clamping out-of-range values first
When marking presence via negation (for first-missing-positive style problems), values outside [1, N] are "unusable" slots. Replace them with a safe sentinel like N+1 before the marking pass so their sign never gets misread.
Bit Manipulation
Hardcoding 32 bits in the bit-count loop
A loop from 0 to 31 works but misses a small optimization: you can stop at the highest set bit of the maximum element. More importantly, hardcoding makes the code fragile if the problem uses 64-bit integers.
Forgetting that Java's % can return negative remainders
In modular exponentiation, (a * b) % mod can give a negative result if intermediate products overflow into a negative value. Cast to long before multiplying, or use Math.floorMod when the sign matters.
Splitting XOR groups incorrectly for two-unique-elements
The rightmost set bit of (A XOR B) guarantees A and B differ at that position. Partition by that bit — every element goes into exactly one group. A common mistake is using the wrong bit mask or forgetting to XOR both groups from scratch.
Recursion
Missing the return value in a recursive helper
When a recursive function computes a value (not just prints), every branch — including the base case — must return something. A missing return on one path silently returns null or 0 in Java and can make the result look correct on happy paths while failing on edge cases.
Exponential time in naive Fibonacci — not memoizing
Plain recursive Fibonacci recomputes the same subproblem exponentially many times. Add a memoization array and check it before recursing — this turns O(2^N) into O(N).
Using linear exponentiation instead of binary exponentiation
Multiplying A by itself N times is O(N). Binary exponentiation squares the result at each step: A^N = (A^(N/2))² — this is O(logN) and becomes critical when N can be 10^9.
Hashing
Decrementing frequency to zero but not removing the key
When tracking a sliding window with a frequency map, set the count to 0 but leave the key — then containsKey returns true even when the element is absent. Always remove the key (or check that the value is > 0) when the count hits 0.
Storing first-occurrence index but also updating it on revisit
For longest-subarray problems, the prefix sum's first occurrence index should never be overwritten. If you see the same prefix sum again, that gap is your candidate — updating the stored index shortens the answer incorrectly.
Sorting & Comparators
Comparing strings by digit value instead of concatenation order
For "largest number" problems, sorting by numeric value gives the wrong order — "9" should come before "34" because "934" > "349". Always compare by concatenating: compare (a+b) vs (b+a) as strings.
Inversion count — incrementing for every remaining element, not just un-picked ones
In merge sort inversion counting, when you pick the right element over the left, the count increases by the number of elements remaining in the left half (not the total left half). Off-by-one here makes every count wrong.
