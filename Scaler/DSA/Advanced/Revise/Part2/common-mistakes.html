Common Mistakes
Part 2 · Days 21–31
Generic pitfalls by technique — not edge cases per problem.
Binary Search on Array (d21, d22)
Wrong mid calculation — integer overflow
(low + high) / 2 overflows when both are large. Write low + (high - low) / 2 always.
Strict loop condition skips the last candidate
while (low < high) exits when low == high, missing the position where the answer lives. Use while (low <= high).
Not shrinking — infinite loop
low = mid or high = mid without ±1 stalls when low and high are adjacent. Always write low = mid + 1 or high = mid - 1.
Returning on first match — wrong for boundary search
For leftmost occurrence: save mid, move high = mid - 1. For rightmost: save mid, move low = mid + 1. Never return immediately on a match.
lower_bound — checking only lb, not lb − 1
lower_bound returns first index ≥ target. The closest value could be at lb - 1. Always compare both and take the smaller absolute difference.
Rotated array — assuming mid splits sorted/unsorted correctly
First determine which half is fully sorted via a[low] <= a[mid]. Then check if target falls inside that sorted half. Only then decide which side to eliminate. Don't guess the split point.
Binary Search on Answer Space (d23)
Wrong lower bound — starting at 0 or 1 instead of max single element
In painters/books, any candidate below the largest single board/book is immediately infeasible — one painter must take that entire piece. Set low = max(single elements), not 0 or 1. Using 0 wastes half the search space and risks passing an invalid candidate to the feasibility check.
Direction confusion — minimize-max vs maximize-min
These two problem types move in opposite directions when the feasibility check passes:
Minimize the maximum (painters, books): check passes → record ans, go left (high = mid - 1). Check fails → go right (low = mid + 1).
Maximize the minimum (aggressive cows): check passes → record ans, go right (low = mid + 1). Check fails → go left (right = mid - 1).
Swapping the direction gives the worst valid answer instead of the best.
Integer overflow in greedy feasibility sums
Board lengths or page counts can be large. currentSum + board can exceed Integer.MAX_VALUE when mid is set near totalSum. Declare running sums as long inside the feasibility check, and use long for the search boundaries (low, high, mid) in painters/books.
Early-exit check placed after the loop — too late
In the feasibility greedy, the "too many workers" check must be inside the loop — the moment a new worker is spawned and the count exceeds the limit, return false immediately. Checking after the loop means you finish assigning all elements even though you already know it's impossible, wasting time and potentially producing wrong results on large inputs.
maxSubArrayFactor — check semantics reversed
The feasibility function returns true when no window of the candidate length exceeds B (length is valid). On true: store K, move low = mid + 1 (try longer). On false: move high = mid - 1. Getting this backwards maximizes rather than the longest valid length.
Forgetting edge cases before the search: students > books, empty input
If there are more students than books, at least one student gets nothing — return -1. If the books array is empty or null, return -1. These checks must come before computing low/high, otherwise the computed bounds are meaningless.
Linked List (d24, d25)
Not saving next before breaking the pointer — loses the rest of the list
In 3-pointer reverse: curr.next = prev breaks the forward link. You must capture next = curr.next first. Order that works every time: next = curr.next → curr.next = prev → prev = curr → curr = next. Skipping the save loses everything after curr with no error — the list is just truncated.
Head deletion treated as a special case — use a dummy node instead
Without a dummy, deleting the head forces an if (head) branch at the top of every function. With a dummy: dummy.next = head. Head deletion and middle deletion are identical: prev.next = curr.next. Return dummy.next. Never write special-case head logic when a dummy is available.
reverseBetween — wrong reconnection order: head before tail
After reversing B..C, the original B-node is now the tail and prev is the new head. Reconnect in this exact order:
1. prevNode.next.next = curr — tail → node after C (curr is the node just past C)
2. prevNode.next = prev — node before B → new head
Doing step 2 first overwrites prevNode.next (which still points to the old B / new tail), so the tail is disconnected from curr forever.
reverseBetween — off-by-one reaching prevNode
prevNode must stop at the node just before position B (1-indexed). Loop for (i = 1; i < B; i++) — runs B−1 times. Writing i <= B or i < B - 1 puts prevNode one position off, causing the entire reconnection to land on the wrong nodes.
reverseKGroup — not counting K nodes before reversing
Before reversing, walk forward K steps and count. If count < K, the tail has fewer than K nodes — return it as-is (per the problem). Reversing without this check processes a partial group and produces a wrong output with no runtime error.
reverseKGroup — not connecting reversed group to the recursive result
After the K-node reverse, head (original first node, now tail of the reversed segment) must point to reverseKGroup(curr, k). Writing head.next = curr skips the recursive reversal — the rest of the list stays in original order.
deleteNode — creating a new node instead of copying the next value in-place
You do not have the predecessor. The trick: copy node.next.val into node.val, then skip node.next via node.next = node.next.next. Creating a new node and trying to swap references fails because external references still point to the original node object.
copyRandomList — wiring original nodes into the clone's pointers
In the 2-pass approach, Pass 1 builds the map original → clone. Pass 2 must use store.get(current.next) and store.get(current.random) to fetch the clone nodes. Writing clone.next = current.next wires the clone's next to the original list node — the clone chain is then entangled with the original instead of being independent.
removeNthFromEnd — negative deleteIndex when B > length
If B equals the list length, deleteIndex = length - B = 0, which correctly removes the head. If B > length (invalid input), the index goes negative. Clamp: if (deleteIndex < 0) deleteIndex = 0. Without the clamp, deleteAtIndex receives a negative index and may return without deleting anything.
Stack (d26, d27)
Pop or peek without isEmpty check
An empty stack throws. Check isEmpty() before every pop and peek — without exception, even when you think the stack cannot be empty at that point.
Matching wrong bracket pair
When a closing bracket arrives, the top must be the exact corresponding opener. Checking only that the stack is non-empty lets mismatched pairs (e.g. [)) pass silently.
Redundant braces — checking for operator after the loop instead of during pop
When popping back to the matching (, track whether any operator was seen among the popped items. This check belongs inside the pop loop, not after it. Checking after loses the state once the loop ends.
Monotonic stack — storing values instead of indices
You need the position of the nearest smaller/greater element, not just its value. Push indices. Access values as a[stack.peek()]. Storing values makes distance calculations impossible.
Trees / BST (d29, d30, d31)
Accessing a child without null check
node.left.val without confirming node.left != null crashes. Handle null as the very first line of every recursive function.
BST validation with int bounds — fails on MIN/MAX_VALUE nodes
Passing Integer.MIN_VALUE / Integer.MAX_VALUE as initial bounds fails when a node holds exactly those values. Use Long.MIN_VALUE / Long.MAX_VALUE.
Not propagating the failure sentinel — balanced tree check
When a helper returns -1 to signal an unbalanced subtree, every parent call must check for -1 before computing its own height. Skipping the check produces a wrong "balanced" answer that bubbles up through all callers.
Off-by-one in tree construction from two traversals
The number of nodes in the left subtree from inorder drives every index calculation. Being off by one silently builds the wrong tree — no error is thrown because the recursion still completes.
