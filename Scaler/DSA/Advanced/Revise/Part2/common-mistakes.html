Common Mistakes
Part 2 · Days 21–31
❌ what you wrote  ·  ✅ what you should write  ·  and why it matters.
Binary Search on Array d21, d22
mid calculation — integer overflow
❌ overflows
mid = (low + high) / 2;
✅ safe always
mid = low + (high - low) / 2;
When low and high are both ~2 billion, their sum wraps to negative. The safe form never adds two large values together.
Loop condition — skips the last candidate
❌ exits too early
while (low < high) { ... }
✅ checks every position
while (low <= high) { ... }
When low == high there is exactly one candidate left. Strict < exits before checking it — the answer is silently missed.
Boundary shrink — infinite loop
❌ range never shrinks
low  = mid;    // stuck when low==mid
high = mid;    // stuck when high==mid
✅ always makes progress
low  = mid + 1;
high = mid - 1;
When low and high are adjacent, mid == low. Setting low = mid leaves low unchanged — the loop spins forever.
Boundary search — returning on first match
❌ finds any occurrence
if (a[mid] == target) return mid;
✅ finds first / last
if (a[mid] == target) {
    ans  = mid;
    high = mid - 1; // leftmost
 // low  = mid + 1; // rightmost
}
A match at mid might not be the leftmost/rightmost. Save mid and keep searching in the correct direction.
lower_bound — checking only lb, not lb − 1
❌ misses the closer value
Return a[lb] directly as the closest.
✅ compare both neighbours
if (lb > 0 && Math.abs(a[lb-1]-t)
         <= Math.abs(a[lb]-t))
    return a[lb - 1];
return a[lb];
lb is the first index ≥ target. The closest value could be at lb - 1. Always check both.
Rotated array — guessing which half contains target
❌ guessing — wrong on edge cases
Directly comparing target to a[mid] without identifying the sorted half first.
✅ identify sorted half first
if (a[low] <= a[mid]) {            // left sorted
    if (t >= a[low] && t < a[mid])
        high = mid - 1;
    else low = mid + 1;
} else {                            // right sorted
    if (t > a[mid] && t <= a[high])
        low = mid + 1;
    else high = mid - 1;
}
One half is always fully sorted. Identify it in O(1), then check if target belongs there. Only then decide which side to eliminate.
Binary Search on Answer Space d23
Lower bound — starting at 0 instead of max(elements)
❌ invalid start — wastes half the range
long low = 0, high = totalSum;
✅ smallest feasible value
long low = maxElement, high = totalSum;
Any candidate below the largest single element is immediately infeasible — one worker must take that whole piece alone. Starting at 0 wastes ~log(maxElement) steps and can pass invalid values to the feasibility check.
Direction confusion — minimize-max vs maximize-min
❌ swapped — gives worst valid answer
// minimize-max (painters):
if (feasible(mid)) low = mid + 1; // ← wrong dir
// maximize-min (cows):
if (feasible(mid)) high = mid - 1; // ← wrong dir
✅ correct directions
// minimize-max: pass → try smaller
if (feasible(mid)) { ans=mid; high=mid-1; }
else               { low=mid+1; }
// maximize-min: pass → try larger
if (feasible(mid)) { ans=mid; low=mid+1; }
else               { high=mid-1; }
These two problem types are mirror images. Minimize-max: when mid works, shrink the upper bound (try smaller). Maximize-min: when mid works, push the lower bound (try larger).
Feasibility sum — integer overflow
❌ overflows silently
int currentSum = 0;
if (currentSum + board > mid) { ... }
✅ use long throughout
long currentSum = 0;
long low = maxEl, high = totalSum;
long mid = low + (high - low) / 2;
if (currentSum + board > mid) { ... }
When mid is near totalSum (which itself can be N × 10⁹), currentSum + board overflows int. Declare all sums and boundaries as long.
Feasibility check — early exit after the loop instead of inside
❌ checks too late
for (int x : items) {
    if (curr + x > mid) { used++; curr = x; }
    else curr += x;
}
if (used > workers) return false; // too late
✅ exit the moment it's impossible
for (int x : items) {
    if (curr + x > mid) {
        used++; curr = x;
        if (used > workers) return false; // inside
    } else curr += x;
}
return true;
Once workers exceed the limit you already know the answer. Finishing the loop wastes O(N) work and, on pathological inputs, can produce incorrect results if overflow occurs.
Linked List d24, d25
3-pointer reverse — not saving next before flipping
❌ loses the rest of the list
curr.next = prev;  // forward link is gone
prev = curr;
curr = curr.next;  // curr.next is now prev!
✅ save → flip → slide → slide
next      = curr.next;  // 1. save first
curr.next = prev;       // 2. flip
prev      = curr;       // 3. slide prev
curr      = next;       // 4. slide curr
Once you flip curr.next, the only way forward is lost. You must save it before touching it. Order is non-negotiable.
Head deletion — special-casing instead of using dummy
❌ branching code, easy to miss cases
if (head.val == val) return head.next;
// ... different logic for middle nodes
✅ dummy makes all positions identical
dummy.next = head;
// prev.next = curr.next  works for ALL positions
return dummy.next;
A dummy node before the real head means head deletion and mid-list deletion are the same operation. One code path, no edge cases.
reverseBetween — connecting head before tail
❌ tail pointer is lost
prevNode.next = prev;        // head wired first
prevNode.next.next = curr;   // prevNode.next now
                             // points to prev, not old-B
✅ tail first, then head
prevNode.next.next = curr; // tail → after C  (1st)
prevNode.next = prev;      // before-B → new head (2nd)
prevNode.next still points to old-B (the new tail) at this moment. Wire the tail first. Once you wire the head (step 2), that reference is overwritten forever.
reverseBetween — off-by-one reaching prevNode
❌ lands on wrong node
for (i = 1; i <= B; i++)   // goes one too far
    prevNode = prevNode.next;
for (i = 1; i < B - 1; i++) // stops one too early
    prevNode = prevNode.next;
✅ stops at B−1 (just before B)
for (i = 1; i < B; i++)    // runs B-1 times
    prevNode = prevNode.next;
prevNode must be the node immediately before position B so that prevNode.next is the first node to reverse. Off by one and the entire reconnection lands on wrong nodes.
reverseKGroup — not counting K before reversing
❌ reverses partial tail group
// directly reverse without checking remaining count
ListNode curr = head; ListNode prev = null;
for (int i = 0; i < k; i++) { ... } // crashes or wrong
✅ count K nodes first
ListNode check = head; int count = 0;
while (check != null && count < k)
    { check = check.next; count++; }
if (count < k) return head; // tail: return as-is
The problem requires leaving the final group unchanged if it has fewer than K nodes. Without the count check you silently reverse a partial group.
reverseKGroup — head.next points to curr, not to recursive result
❌ rest of list stays unreversed
head.next = curr; // skips recursive reversal
✅ tail connects to next reversed group
head.next = reverseKGroup(curr, k); // recurse
After reversing K nodes, head is now the tail of this group. It must connect to the result of reversing the next group — not to curr directly.
deleteNode — creating a new node instead of mutating in place
❌ external refs still point to original
Creating a new node and trying to swap references. External pointers still hold the original node's address — nothing changes for them.
✅ copy-next trick
node.val  = node.next.val;
node.next = node.next.next;
You don't have the predecessor, so you can't unlink this node. Instead, disguise it as its successor by copying the next value in, then remove the successor.
copyRandomList — wiring originals instead of clones
❌ clone entangled with original list
clone.next   = curr.next;    // points to original node
clone.random = curr.random;  // points to original node
✅ always go through the map
clone.next   = map.get(curr.next);    // null-safe
clone.random = map.get(curr.random);  // null-safe
map.get(null) returns null — no null check needed. If you wire curr.next directly, the clone's chain points into the original list. Not a deep copy.
Stack / Monotonic Stack d26, d27
Pop or peek without isEmpty check
❌ throws on empty stack
char top = stack.pop(); // EmptyStackException
✅ always guard first
if (!stack.isEmpty()) {
    char top = stack.pop();
}
Even when you're sure it can't be empty — check. The one time you're wrong causes a crash with no useful error message.
Bracket matching — checking non-empty instead of exact pair
❌ lets mismatched pairs pass
if (!stack.isEmpty()) stack.pop(); // [) passes!
✅ verify exact counterpart
if (stack.isEmpty() || stack.pop() != matchOf(c))
    return false;
Non-empty only proves something is on the stack — not that it's the right thing. [) is invalid but passes the non-empty check.
Redundant braces — operator flag checked after the pop loop
❌ flag state is lost after loop
while (stack.peek() != '(') stack.pop();
stack.pop(); // remove '('
if (!hasOp) return true; // hasOp never set
✅ track operator inside the loop
while (stack.peek() != '(') {
    hasOp |= isOperator(stack.peek()); // inside
    stack.pop();
}
stack.pop(); // remove '('
if (!hasOp) return true;
You must inspect each popped character before discarding it. After the loop the characters are gone.
Monotonic stack — pushing values instead of indices
❌ can't compute distances
stack.push(a[i]); // value — position is lost
✅ push index, access value via a[i]
stack.push(i);                  // index
// compare: a[stack.peek()] > a[i]
// answer:  nsr[stack.pop()] = i
The answer for each element is its position, not its value. You need i - stack.peek() for distances or nsr[popped] = i for the next-smaller index. Values don't give you that.
Trees / BST d29, d30, d31
Accessing child without null check
❌ NullPointerException on leaf nodes
int solve(TreeNode node) {
    return node.left.val + solve(node.right);
}
✅ null check is always line 1
int solve(TreeNode node) {
    if (node == null) return NEUTRAL;
    int left  = solve(node.left);
    int right = solve(node.right);
    return combine(left, right, node.val);
}
Every tree recursion must handle null first. Leaves have null children. There are no exceptions.
BST validation — int bounds fail on MIN/MAX_VALUE nodes
❌ fails when node.val == Integer.MIN_VALUE
isValid(root, Integer.MIN_VALUE, Integer.MAX_VALUE)
// node.val <= min fails when val IS min
✅ long bounds have no overlap
isValid(root, Long.MIN_VALUE, Long.MAX_VALUE)
// node.val (int) can never equal Long.MIN/MAX
A node holding exactly Integer.MIN_VALUE must satisfy val > min_bound. If min_bound is also Integer.MIN_VALUE the check val > min is false even for a valid node.
isBalanced — not propagating the -1 sentinel upward
❌ wrong answer bubbles up as a valid height
int left  = height(node.left);
int right = height(node.right);
// forgot to check if left or right == -1
return 1 + Math.max(left, right);
✅ check sentinel before using the value
int left  = height(node.left);
int right = height(node.right);
if (left == -1 || right == -1) return -1;
if (Math.abs(left - right) > 1) return -1;
return 1 + Math.max(left, right);
Once any subtree returns -1 (unbalanced), every ancestor must pass -1 up immediately. Using -1 in a Math.max calculation silently produces a garbage height that looks valid.
Tree reconstruction — off-by-one in index slicing
❌ wrong split — silent garbage tree
int k = inMap.get(pre[ps]);
// left subtree preorder ends at ps + k (off by 1)
root.left  = build(pre, ps+1, ps+k, ...);
root.right = build(pre, ps+k, pe, ...);
✅ leftCount = k - inStart drives everything
int k = inMap.get(pre[ps]);
int leftCount = k - is;    // nodes in left subtree
root.left  = build(pre, ps+1,            ps+leftCount, in, is,  k-1, inMap);
root.right = build(pre, ps+leftCount+1,  pe,           in, k+1, ie,  inMap);
The number of nodes in the left subtree (k - inStart) is the single source of truth for all index arithmetic. Derive every slice from it — never guess.
